# 案例：派单 → 施工 → 验收（聊天定方案，电脑和掌机上的施工队自己开工）

## 怎么搭
- 一条队：pc-butler 的 `orders` 分支。`电脑/NNN.md`、`掌机/NNN.md`；认领写 `<文件夹>/认领/NNN.md`，谁先推上去算谁的；做完改名 `已完工_NNN.md`；先放着 `暂缓_`，不做了 `撤销_`（开头写一句为什么）。编号接着整条分支最大的往下排。
- 单子头三行：第一行「建议模型 ｜ 档位 ｜ 一句理由」（判法见 `_ops/模型选择.md`），第二行标题，第三行「仓库：…」。
- 施工队：电脑「电脑自动工」、掌机「掌机自动工」，都是后台的 Claude Code 会话，照第一行开模型和档位。按仓库分道：碰的仓库有一个相同就排在一个会话里接着干，一个都不同就同时开（电脑最多 2 个、掌机最多 4 个）。同一道、模型档位一样的下一张，做完接着认领，连做 5 张收工。
- 派单员在电脑上跑；电脑掉线超过一阵，掌机接手，电脑回来再还。
- 写单的人（聊天这边）：先翻 `_ops/案例/`；写清楚 Song 的原话、要做成什么样、底线、怎么验；单子越细，模型可以越低。开工了跟 Song 说一声，不等他喊。
- 验收：读完工报告，真机要 Song 点的写成一步一行；他的修改和抱怨记进 `_ops/模型试用记录.md`。

## 坑（踩过的）
- 后台会话的状态要从 `claude agents --json` 那一处读，别自己猜（061：一个早退的会话挂在列表里，新单一直开不起来）。
- 喊一个已经在跑的会话要带「再喊一次」，不然以为开过了就不喊（102）。
- 推送一律先 `git pull --rebase` 再推，推不上去就再拉再推；不许 `--force`。orders 分支用写全的 refspec 拉，别让它 rebase 到 main 上。
- 跑着的会话不会重读单子：单子开工以后再改，它看不见。要改就写新单，或者等它完工。
