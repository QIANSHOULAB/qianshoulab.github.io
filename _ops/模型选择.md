# 施工单选模型（任何窗口、任何会话，只要提到施工单就先读这一页）

Song 的额度是一个池子，聊天和 Code 共用。模型选高了，池子先干。所以每张施工单都要带一行建议模型。

## 派单去哪（写单的先看这条）
- 默认派给 Song 电脑上常驻的施工队：单子写成 `F:\songchengmin\施工单\待施工_NNN_名字.md`（编号接着最大的往下排，格式照那个文件夹的 README.md），聊天这边用电脑桥写进去。大管家看到新单 2 分钟内喊施工队开工，Song 一句话都不用说。
- 本仓库 `_ops/施工单队列.md` 只给 Song 亲手开的云会话。写在这里，施工队看不见：11-11 公益站单就这么漏接过。
- 单子要新建公开仓库的（网站类）：派单前聊天这边先把空仓库建好（照 gua-github 技能用 Chrome 建，建不了就请 Song 建），单子里写明仓库已在。施工队自己建公开仓库会被它的权限系统拦下（009、021 都卡过）。

## 谁来写
写施工单的那个 Claude，在单子第一行写：

`建议模型：Haiku / Sonnet / Opus ｜ 一句理由`

已经有的老单子没写的，接手的 Claude 按下面的表自己判一次，把这行补到单子第一行。

## 怎么判
- Haiku：纯体力活。批量改字、改版本号、打包、跑固定测试、按清单搬文件。
- Sonnet：默认。改界面、双语、上架材料、返工、写文案、跑 e2e。拿不准就写它。
- Opus：只给三种。从零做新产品；跨很多文件的大改结构；查不出原因的硬 bug。
- Fable：施工不用，不写进建议里。验收、装机、跟进也不用 Fable（2026-11-12：一天的 Fable 验收烧掉大半周额度），只在定大方案时开。

## 分工：谁用高档，谁用低档
- 写单的会话：Song 开最高档（一般 Max）。想得全，坑都在单子里踩完。写单的 Claude 还要负责判「建议模型」。
- 干活的会话：Song 就按单子第一行的建议模型开，不再往上加一档。省下的额度就是这么来的。
- 所以单子的详细程度，跟执行模型成反比：执行的模型越低，单子越要写到不用动脑。

## 单子要写多细
- 建议 Haiku：逐步照抄级。每一步写明改哪个文件、哪一行、改成什么原文，给出要跑的命令，写明怎样算过。不留任何要它判断的地方。
- 建议 Sonnet：写清目标、涉及的文件、规矩出处（设计规范、文案规范）、判的标准、已知的坑。具体怎么改它自己定，但容易走偏的地方要点名。
- 建议 Opus：写清目标、边界、判的标准，路线让它自己选。只写它容易漏掉的底线。
- 写单时如果发现需要的细度已经接近「逐步照抄」，说明这活该给 Haiku，别写成 Sonnet 级的简单单子。反过来，写不细的活（有很多要判断的地方），不要硬降档，老老实实给 Sonnet 或 Opus。

## 自动化到哪一步
- 定时任务：创建和更新时模型由我直接设，不用 Song 管。
- 手开的施工会话：模型只能开会话的人选，Claude 这边切不了。能做到的最远是：单子第一行写明、会话开头的 Claude 读到后报一句「这张单建议 X，当前是 Y」，高了或低了就提醒 Song 换。

## 每个会话开头要做的事
1. 读本页。
2. 看自己当前是什么模型。
3. 和单子第一行对比，差两档以上（比如单子写 Haiku 却开着 Opus）就先说一句再开工。
4. 一张单子一个会话，做完关，别接着聊下一张。

## 试用记录
试行期间，每张单做完后 Song 提的修改和抱怨，记进 _ops/模型试用记录.md，规则看那一页。接到施工单、写返工单、听到 Song 评价产品时都要想到这件事。
