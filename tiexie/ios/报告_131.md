## 做了什么

- `App/FirebaseMailbox.swift`（新，单独一个文件）：
  - `FBConfig`：认大管家递来的 `kind2=config` 那封，存钥匙串（`backup-config`）；不是 `firebase-rtdb`、不是 https、`apiKey` 空的都不认。
  - `FBAuth`：匿名登录（`accounts:signUp`），idToken 提前 5 分钟换（`securetoken`），换不成就重新登录，refreshToken 存钥匙串（`backup-auth`）；401 换令牌再试一次。
  - `FBMailbox`：一封信 = 密文 base64、每片 ≤ 1 000 000 字写 `p/0…p/n-1`、最后写 `meta {at:{.sv}, n, size}`；办完 `DELETE` 整封 = ack；`seen/phone` 写 `{.sv:timestamp}`。一封最大 10 MB，超了不收（走 Cloudflare）。
  - `FBInbox` + `FBStream`：用 `text/event-stream` 听 `to_phone`，不轮询；`put`/`patch`、数组形式的 `p`、`keep-alive`、`cancel`/`auth_revoked` 都认；meta 和所有片到齐、字节数对得上才算一封；断了 2、5、10、30、60… 秒退避重连，75 秒没动静算断，50 分钟主动重连。
  - `BackupRoute`：什么时候换管子。寄失败（连不上、5xx、429、4xx 除 413）或「网在、WebSocket 断了超过 60 秒」→ 备用模式；Cloudflare 连续好 5 分钟（WebSocket 不断、期间没寄失败）→ 回去。
  - `SeenLetters`：两条路都来的同一封只办一次，键 = 信的 id + `data` 的摘要（点钞机 first / final 同一个 id、内容不同，不会互相吞）。
- `App/Butler.swift`：所有寄信（发件箱、hello、点钞机、「收到」）统一走 `deliver`：平时 Cloudflare，叫不应这一封改走 Firebase，备用模式下直接走 Firebase（Firebase 也不通再试 Cloudflare）。进备用模式才开流、每 60 秒写 `seen/phone`；回去就关流。收信两条路共用一个 `process`。收到配置：存钥匙串、建管子、回 `fb-config-ok`。
- `App/Keychain.swift`：加了 `account` 参数（默认值跟原来一样，配对照旧存在 `pair.bin` 退路里）。
- 设置里大管家那一栏：有配置多一行「备用通道：有」，正走备用时多一行小字「走备用通道」，不弹提示。解除配对不清配置（它不属于哪个信箱）。
- 点钞机（122）、发件箱（120）本来就走 `Butler`，对换管子透明，没动它们。
- 版本 0.2.1 → 0.3.0（build 4），`release-notes.md` 写了一句人话。

## 测过什么

CI（GitHub Actions macOS 26、Xcode 26.6、iPhone 模拟器）：整套单测过，包括新加的 `FirebaseMailboxTests`（全用假 Firebase，`FakeFirebase` 假登录 + 假数据库，不碰真的谷歌）：

- 配置：认对的、不认类型不对 / http / 缺字段 / kind2 不对的。
- 登录：首次登录、缓存、到点换新、存下的 refreshToken 优先、换不成重新登录；401 换令牌重试一次。
- 寄信：2.3 MB 的密文切成 4 片、每片 ≤ 1 000 000 字、meta 最后写、meta 里 n 和 size 对；超 10 MB、id 不对不收；删整封。
- 收信整条链：假大管家用同一套 AES-GCM 封信 → 假 Firebase → 事件树（对象和数组两种写法）→ `FBInbox` → 手机拆开，文件也在；同一棵树再来一遍不重复；方向不对拆不开。
- 事件：meta 没到不算、少一片不算、字节数对不上不算、删了又来同名的算新的、patch、`cancel`/`auth_revoked`、keep-alive、坏 JSON。
- 换管子：错误分类（URLError、500/1101、429、404 换；413、tooBig、坏信不换）；寄失败 → 备用 → 好满 5 分钟回去、中途又失败重新数；WebSocket 断 60 秒才换、没网不换。
- 去重：同一封两条路只办一次，first / final 不互相吞。

## 没验到的

- **真的谷歌**：没碰。配置（apiKey、databaseURL）掌机不读（钥匙文件不读），测试全是假服务器。真登录、真规则（`/boxes/$box`）、真流的 `keep-alive` 节奏、`.sv` 时间戳，要等 Song 的手机真收到配置后才知道。
- **真手机**：LiveContainer 里钥匙串能不能写（写不进会退到 app 数据文件夹，同配对的做法）、`URLSession.bytes` 在 LiveContainer 里能不能长连、app 退后台流会不会被系统掐（会掐，回前台重连，信在 Firebase 里不丢）。
- **大管家递配置那封的真实样子**：照 129 的 `docs/备用信箱.md` 做的（`data.kind2=config`、`data.id=cfg-…`、`data.backup`），没跟真大管家对过。
- 「回去」的 5 分钟、「WebSocket 断 60 秒」是纯逻辑单测过，没真断网试。
- 版本发出去以后，Song 装不装得上没验。

## 我替你定了这些

- 手机退后台就关流、回前台重新判断（备用模式的状态不留，回前台第一封寄失败再进）。后台不写 `seen/phone`。
- 备用模式下 Firebase 寄不出去，这一封再试一次 Cloudflare，不丢。
- 去重键用「id + data 摘要」而不是只看 id：不然点钞机 first / final 同一个 id 会被吞掉一封。
- 「有没有网」用系统的 `NWPathMonitor`（`RouteNetProbe`，不发包）：没网时 WebSocket 断多久都不算 Cloudflare 的事，不进备用。
- 配置用钥匙串存，写不进就退到 app 数据文件夹（只有这个 app 看得见）。
- 只动了 `tiexie/ios/`，工作流文件一个字没改。
